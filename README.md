# Инвентар

Универсална система за инвентар за всякакъв тип бизнес, пригодена за българския пазар: артикули с
персонализирани полета, наличности по складове, поръчки и пратки, себестойност, фактури по ЗДДС, абонаменти,
мобилен режим без връзка и интеграции с куриери (Еконт, Спиди, BOX NOW), онлайн магазини (WooCommerce,
Shopify) и счетоводни програми.

## Технологии

| Слой | Избор | Защо |
|---|---|---|
| Език | **TypeScript** навсякъде | един език за интерфейс, сървър и схема на базата |
| Framework | **Next.js 16** (App Router, Server Actions, Route Handlers) | страници, сървърна логика и REST API в един проект |
| База данни | **MySQL 8** чрез **Drizzle ORM** (mysql2) | **една база на клиент** + контролна база; работи на Hostinger и всеки MySQL/MariaDB |
| Стилове | **Tailwind CSS 4** | малка, консистентна дизайн система в `src/app/globals.css` |
| Други | lucide-react (икони), date-fns (дати, bg локал), html5-qrcode (камера) | |

## Архитектура: един клиент = един поддомейн = една база

- **Контролна база** (`CONTROL_DATABASE_URL`): организации, потребители, членства, сесии и пул от бази.
  Схема: `src/db/control-schema.ts`, миграции: `drizzle/control`.
- **База на клиента**: всички данни на организацията (артикули, наличности, поръчки, пратки, API ключове,
  webhooks, одит). Схема: `src/db/tenant-schema.ts`, миграции: `drizzle/tenant`, прилагат се към всяка база.
- **Поддомейн**: `<поддомейн>.APP_DOMAIN`. Клиентът се определя от `Host` заглавието (`src/lib/tenant.ts`),
  връзката към неговата база се кешира (`src/db/tenant.ts`). Основният домейн показва портала
  (вход, списък организации, създаване на организация).
- **Създаване на организация** (`provisionTenant`): в режим `auto` приложението изпълнява `CREATE DATABASE`
  и миграциите; в режим `manual` взема предварително създадена база от пула (`pnpm db:pool:add`).
- Потребител може да е член на няколко организации с различни роли; сесията е обща за всички поддомейни
  (cookie за `.APP_DOMAIN`), освен на `localhost`, където всеки поддомейн има отделен вход.

## Стартиране

```bash
pnpm install
cp .env.example .env          # APP_DOMAIN, бази, APP_SECRET
docker compose up -d mysql    # MySQL 8 на порт 3307
pnpm db:migrate               # контролна база + всички клиентски бази
pnpm db:seed                  # демо: организации demo и vtora
pnpm dev -p 3100              # портал: http://localhost:3100 · клиент: http://demo.localhost:3100
```

Портът трябва да съвпада с `APP_DOMAIN` в `.env` (напр. `APP_DOMAIN=localhost:3100`). Ако портът е зает,
Next.js тихо избира друг и приложението не отговаря на адреса от `APP_DOMAIN`.

Демо вход след `db:seed`: **admin@demo.bg / demo1234** (собственик на demo и vtora) и
**sklad@demo.bg / demo1234** (служител в demo). Браузърите резолват `*.localhost` към 127.0.0.1 без настройки.

**Имейл.** Забравена парола и покани за нови потребители се изпращат по SMTP (`SMTP_HOST`, `SMTP_PORT`,
`SMTP_USER`, `SMTP_PASS`, `MAIL_FROM` в `.env`). Без `SMTP_HOST` писмата (с линковете) се печатат в конзолата
на сървъра — удобно за разработка.

**Снимки на артикули.** Качват се от страницата на артикула или през API (`POST /api/v1/items/{id}/images`).
Записват се като WebP (до 1600px + миниатюра 400×400, без EXIF/GPS) в `STORAGE_DIR` (по подразбиране `./storage`),
в подпапка за всеки клиент. Папката трябва да се архивира заедно с базите и да е извън папката на деплоя,
ако тя се презаписва.

**Тестове.** `pnpm test` (Vitest) пуска unit тестове и интеграционни тестове срещу истински MySQL: складовото
ядро (партиди, серийни номера, трансфери), пратки и изпълнение на поръчки, провизиране, изолация между клиентите
и права на API ключовете. Тестовете създават собствена контролна база и клиентски бази с префикс `inv_test_`
на сървъра от `CONTROL_DATABASE_URL` и ги изтриват накрая; данните за разработка не се докосват.
Друг сървър/потребител: `TEST_DATABASE_URL=mysql://root:root@127.0.0.1:3306`; друг префикс: `TEST_DB_PREFIX`
(трябва да съдържа „test“). GitHub Actions (`.github/workflows/ci.yml`) пуска typecheck, lint, тестове и build.

Други скриптове: `pnpm db:backup`, `pnpm db:generate` (нови миграции след промяна на схема), `pnpm db:pool:add`,
`pnpm db:euro` (превалутиране от лева в евро), `pnpm platform-admin <имейл>`, `pnpm typecheck`, `pnpm lint`,
`pnpm test`, `pnpm build`, `pnpm db:studio`. Периодичните задачи (`notify:digest`, `carriers:sync`,
`shops:sync`, `orgs:purge`) са описани в „Работа в production“.

## Работа в production

- **Миграции при стартиране.** Сървърът прилага миграциите към контролната и към всички клиентски бази при
  всяко стартиране (`src/instrumentation.ts`, със заключване в MySQL при няколко процеса). Неуспешна база се
  записва в лога и в `/api/health`; `AUTO_MIGRATE=0` изключва автоматичните миграции (тогава `pnpm db:migrate`).
- **Проверка на състоянието.** `GET /api/health` (без вход): 200 и `{"status":"ok"}` при работеща контролна
  база, 503 иначе; версия, време от стартиране, брой отворени пулове към клиентски бази, резултат от миграциите.
  Подходящо за uptime мониторинг.
- **Логове.** JSON по един ред (`time`, `level`, `msg`, …) в stdout/stderr. Всяка необработена грешка на сървъра
  (`request.error`) и в браузъра (`client.error`) се записва; страницата за грешка показва код (digest), по който
  записът се намира в лога. С `SENTRY_DSN` грешките отиват и в Sentry.
- **Архиви.** `pnpm db:backup --keep 14` записва `mysqldump` на контролната и на всяка клиентска база (gzip) и
  архив на `STORAGE_DIR` в `backups/<дата_час>/` с `manifest.json`, и изтрива архивите, по-стари от 14 дни.
  Изисква `mysqldump` и `tar`. Пример за cron (всяка нощ в 03:15) на VPS или в hPanel › Cron Jobs:

  ```
  15 3 * * * cd /home/<user>/inventar && pnpm db:backup --keep 14 >> backups/backup.log 2>&1
  ```

  Възстановяване на една база: `gunzip < backups/<дата>/inv_demo.sql.gz | mysql -u <user> -p inv_demo`.
  Копирайте архивите и извън сървъра (напр. rclone към облачно хранилище).
- **Известия.** Камбанката в менюто и страницата „Известия“ показват ниска наличност, закъснели пратки и
  партиди с изтекъл или изтичащ (до 30 дни) срок. `pnpm notify:digest` изпраща дневен имейл с тях до
  мениджърите и администраторите (без известия — без писмо; най-много веднъж на ден; изключва се от профила).
  Cron: `30 7 * * * cd /home/<user>/inventar && pnpm notify:digest >> digest.log 2>&1`.
- **Куриери.** `pnpm carriers:sync` проверява статусите на товарителниците (доставена → пратката се приключва,
  върната → отказва) и записва събрания наложен платеж. Cron (всеки час):
  `0 * * * * cd /home/<user>/inventar && pnpm carriers:sync >> carriers.log 2>&1`.
- **Онлайн магазини.** `pnpm shops:sync` внася новите поръчки и изпраща променената наличност. Cron (на 5 минути):
  `*/5 * * * * cd /home/<user>/inventar && pnpm shops:sync >> shops.log 2>&1`.
- **Изтриване на организации.** Собственикът заявява изтриване от Настройки; след 30 дни `pnpm orgs:purge`
  изтрива базата, снимките и членствата (`--dry-run` за проверка). Cron (всеки ден):
  `30 3 * * * cd /home/<user>/inventar && pnpm orgs:purge >> purge.log 2>&1`.
- **Правни данни и контакт.** `LEGAL_COMPANY_NAME`, `LEGAL_COMPANY_EIK`, `LEGAL_COMPANY_ADDRESS`,
  `LEGAL_CONTACT_EMAIL`, `LEGAL_DPO_EMAIL`, `LEGAL_HOSTING` попълват Общите условия, Политиката за
  поверителност, бисквитките и договора за обработка (DPA); `PLATFORM_CONTACT_EMAIL` е контактът за абонамент.
  Без тях страниците показват заместващ текст — попълнете ги преди първия клиент.

## Деплой (Hostinger или друг хостинг)

1. **Node.js.** Next.js е сървърно приложение: нужен е план с Node.js (Hostinger VPS, или споделен план,
   който изрично поддържа Node.js приложения). Статичният хостинг не е достатъчен. Стартиране:
   `pnpm build && pnpm start` (или чрез PM2/systemd на VPS).
2. **Домейн.** `APP_DOMAIN=inventar.bg`, `APP_PROTOCOL=https`. DNS: A запис за `inventar.bg` и **wildcard**
   `*.inventar.bg` към сървъра. SSL трябва да покрива wildcard-а (Let's Encrypt с DNS предизвикателство,
   или Cloudflare пред сървъра). На споделен хостинг добавете поддомейните ръчно в hPanel, ако wildcard не
   се поддържа.
3. **Бази.** На VPS: `TENANT_DB_MODE=auto` с MySQL потребител с право `CREATE`. На споделен хостинг
   (без право за CREATE DATABASE): `TENANT_DB_MODE=manual`, създайте базите в hPanel и ги добавете в пула с
   `pnpm db:pool:add <база> <потребител> <парола> <host>`; всяка нова организация взема следващата свободна.
   Миграции при нова версия: `pnpm db:migrate` обхожда всички клиентски бази.
4. **Секрети.** `APP_SECRET` е задължителен (сесии и криптиране на паролите на базите в пула).
5. **Демо без поддомейни.** Ако хостингът не може да приема `*.APP_DOMAIN` (напр. Node.js приложение на
   споделен план), `DEMO_TENANT=demo` превръща целия сайт в тази една организация: адресите са без
   поддомейн, а порталът, регистрацията и `/admin` не се ползват. Нужни са две бази (контролна + `inv_demo`
   в пула), после `pnpm db:migrate && pnpm db:seed`.
6. **Build.** `pnpm build` е с webpack: Turbopack пуска отделни Node процеси за CSS, а споделеният хостинг
   (Node.js приложение на Hostinger) не го позволява. `pnpm dev` е с Turbopack.

## Функционалности

### Основа
- **Табло**: показатели, ниска наличност с бутон за поръчка, последни движения, следващите 7 дни,
  стойност по категория и по локация, изтичащи партиди.
- **Категории** с **персонализирани полета** (текст, число, дата, избор, да/не, „задължително“).
- **Артикули**: код, баркод, описание, минимум, мерна единица, цени, архивиране, динамични полета,
  **варианти** (размер/цвят със собствен код и наличност), **партиди със срок на годност** или
  **серийни номера** (FEFO подредба, предупреждения за изтичане), пълна складова история с потребител.
- **Локации**: няколко склада/магазина, наличност по локация, **трансфери** между локации, локация
  по подразбиране.
- **Складови движения**: приход / разход / точно количество / трансфер; всяка промяна с причина и потребител.
- **Партньори**: доставчици и клиенти с контакти, ДДС номер, срок на доставка, история.
- **Поръчки**: за доставка (от доставчик) и клиентски; чернова → потвърдена → частично → изпълнена;
  **пратка за оставащото** с един бутон, частични доставки и остатъци.
- **Пратки**: входящи/изходящи с редове, партиди/серийни номера по ред, локация, партньор, куриер,
  проследяване; доставката прилага наличността в една транзакция и обновява поръчката.
- **Колекции**: свободно групиране на артикули.
- **Календар**: очаквани пратки, изтичащи партиди, собствени събития, напомняния, крайни срокове.
- **Сканиране**: камера на телефона (html5-qrcode) или USB/Bluetooth скенер; бърз приход/разход;
  непознат баркод → създаване на артикул с него.

### Склад и документи
- **Печат (PDF)**: етикети с баркод (A4, 3 × 8), стокова разписка / приемателен протокол / протокол за връщане,
  справка за наличност, лист и протокол за инвентаризация. Данните на фирмата — Настройки › Данни за документи.
- **Инвентаризация**: броене по локация със скенер (USB или камера), разлики и корекция в една транзакция.
- **Връщания** от клиенти и към доставчици по поръчка, с отчитане на върнатото количество.
- **Известия**: камбанка, страница „Известия“ и дневен имейл (ниска наличност, закъснели пратки, срокове).
- **Първи стъпки** за нова организация: бърз старт, CSV импорт, демо данни, които се изтриват с един бутон.
- **Няколко доставчика на артикул** с цена, код при доставчика, минимално количество и срок на доставка;
  предпочитан доставчик.
- **Опаковки** (кашон, палет) с коефициент и собствен баркод: сканиране на кашон отчита 12 бр.
- **Предложения за поръчка** (Поръчки › Предложения): колко да се поръча от всеки доставчик според
  продажбите, срока на доставка, минимума и очакваното; създава чернови на поръчки по доставчик.
- **Мобилен режим** (`/m`): приложение за телефона (PWA, инсталира се от браузъра) за прием, изписване,
  трансфер и броене със скенер или камера; работи и без връзка — операциите се пазят на телефона и се
  изпращат веднъж при връзка (без дублиране).
- **Помощ** (`/help`): кратки ръководства на български за основните процеси; „?“ до заглавието на страниците.

### Пари, ДДС и фактуриране
- **Точни суми**: цени decimal(14,4), количества decimal(14,3) (кг, л, м — знаци след запетаята по артикул),
  аритметика без грешки от плаваща запетая. Евро от 1.1.2026; организации в лева се превалутират по
  1,95583 (`pnpm db:euro` или бутон в Настройки), документите пазят оригиналните суми.
- **Себестойност**: всяко движение има стойност; оценка по средно претеглена цена или FIFO; стойност на
  склада към дата, себестойност на продажбите и марж по артикул и клиент.
- **ДДС**: ставки на организацията (20 %, 9 %, 0 % с основание, без ДДС), по артикул, категория и ред.
- **Фактури** по ЗДДС: фактура, кредитно и дебитно известие с пореден десетразряден номер, проформа;
  издаване със снимка на страните, PDF, имейл, плащания и просрочени. Протокол за брак, поредни номера
  без дупки за всички документи. Проверка на ЕИК/ЕГН и VIES. Експорт за счетоводителя (CSV) и файл за
  счетоводна програма (виж „Интеграции“).
- **Извън обхвата**: касови бележки и продажба на дребно. Софтуер, който издава фискални бонове, трябва да
  отговаря на Наредба Н-18 и да е регистриран в НАП (СУПТО) — за магазин се свързва със съществуващ
  касов софтуер, не го замества.

### Анализи (Отчети)
Параметри по организация (Настройки): прозорец за анализ, дни за залежала стока, срок на доставка,
буфер за сигурност, целеви марж. Отчети: стойност на склада по месеци, оборот и марж по категория,
най-продавани, **предложения за поръчка** (средна дневна консумация × покритие + минимум − наличност −
очаквано), залежала стока, възраст на наличността, изтичащи партиди.

### Абонаменти и данни
- **Планове** (три нива, редактират се в `/admin`): лимити за потребители, артикули, локации, фактури за
  месеца и интеграции. 14 дни пробен период; при изтекъл или неплатен абонамент — 7 дни гратисен период,
  после само преглед и експорт (данните не се трият). Статусът и „платено до“ се водят ръчно в `/admin`,
  докато бъде избран доставчик на онлайн плащания.
- **Правни страници** (`/terms`, `/privacy`, `/cookies`, `/dpa`), приемане на условията при регистрация.
- **GDPR**: пълен експорт на данните на организацията (ZIP с CSV на всяка таблица и снимките) и заявка за изтриване
  с 30 дни за отказ.

### Потребители и организации
- Вход с имейл и парола (scrypt, сесии в базата, httpOnly cookie). SSO не е включен на този етап.
- **Профил** (`/profile`): име, парола, сесии, дневен имейл; **двуфакторна защита (TOTP)** с QR код за
  Google/Microsoft Authenticator и 10 еднократни кода за възстановяване; новата парола по линк не заобикаля кода.
- **Забравена парола** и **покани по имейл** (еднократни линкове); смяната на паролата прекратява другите сесии;
  „Изход от всички устройства“.
- **Защита**: до 5 грешни опита за вход на имейл и 20 на IP за 15 минути; заглавия за сигурност (CSP и др.);
  до 600 API заявки в минута на ключ.
- **Роли**: собственик, администратор, мениджър, служител, само четене; проверка на всяко действие.
- **Няколко организации** (multi-tenant): всяка със собствена база данни и поддомейн; един потребител
  може да е член на няколко и превключва от страничното меню или портала.
- **Одит**: кой какво е променил, с детайли, филтри и търсене.
- **Администрация на платформата** (`/admin` на основния домейн): всички организации със статус, база,
  собственик и брой потребители; спиране/активиране (спряна организация вижда съобщение, API връща 503);
  повторен опит за неуспешна подготовка; пул от бази (режим manual). Права: `pnpm platform-admin <имейл>`.

### Интеграции
Настройват се в Настройки › Интеграции (данните за достъп се пазят криптирани, всяка заявка се записва в
дневник, временните грешки се повтарят) и са достъпни според плана.
- **Куриери — Еконт, Спиди, BOX NOW**: товарителница от изходящата пратка до офис/автомат (списък с търсене)
  или адрес, с наложен платеж (по подразбиране сумата на поръчката), тегло и брой пакети; етикет за печат;
  статусите се обновяват автоматично и приключват пратката; справка „Наложен платеж“ (Отчети) за
  равнение на събраното и изплатеното. Еконт има демо среда за тест.
- **Онлайн магазини — WooCommerce и Shopify**: свързване на артикулите с продуктите и вариантите по SKU;
  наличността към магазина е на склад минус неизпълненото по потвърдени продажби (изпраща се само
  промененото); поръчките от магазина влизат като потвърдени продажби без дубли, с клиент и цени.
- **Счетоводни програми** (Microinvest Делта Pro, Ажур, Плюс-Минус и др.): Отчети › За счетоводителя ›
  „Файл за счетоводна програма“ — ред на документ и ставка ДДС, кодировка Windows-1251 или UTF-8, разделител,
  десетичен знак и формат на дата по избор. Колоните се съпоставят веднъж в импортния филтър на програмата.
- **Преминаване от Microinvest Склад Pro**: импортът на артикули чете Windows-1251 и табулация и разпознава
  колоните от експорта на стоките (Код, Име, Баркод1, Мярка, Група, Доставна цена, Цена на дребно); импорт на
  партньори (Фирма, Булстат, Данъчен номер, МОЛ, Град, Адрес…) с проверка на ЕИК и ДДС №.
- **CSV импорт** на артикули (преглед преди запис, upsert по код, автоматични категории, наличности по
  локация) и на партньори; **CSV експорт** на артикули, наличности по локации и движения.
- **REST API** `/api/v1/*` с API ключове (четене / запис) — артикули, наличности, движения, пратки
  (вкл. смяна на статус), поръчки, локации, партньори, категории.
- **API документация**: `/api/v1/openapi.json` (OpenAPI 3.1 спецификация), `/docs/api/swagger` (Swagger UI с
  Authorize и Try it out) и `/docs/api` (четима версия на български, генерирана от същата спецификация, с
  webhooks и примери за проверка на подписа). Източник: `src/lib/openapi.ts`.
- **Webhooks**: POST с HMAC-SHA256 подпис за събития (създаден/променен артикул, ниска наличност,
  движение, пратка, поръчка), с журнал на доставките и тестово събитие.

## Структура на проекта

```
src/
  app/            маршрути (по една папка на страница), layout, глобални стилове
  components/
    layout/       странично меню
    ui/           бутони, полета, карти, етикети, таблици, празни състояния
    items/        ItemForm (динамични полета)
    shipments/    ShipmentForm (динамични редове), товарителница
    orders/, partners/, scan/, settings/, auth/
  db/             control-schema.ts, tenant-schema.ts, control.ts, tenant.ts (пул + provisioning), migrate.ts, seed.ts
  lib/
    actions/      server actions (всички записи; всяко действие взема ctx.db и проверява роля)
    queries.ts    всички четения (приемат базата на клиента)
    tenant.ts     поддомейн → организация
    stock.ts      двигател на наличностите: локации, партиди, серийни номера, трансфери
    shipment-service.ts  доставка на пратка (общо за UI и API)
    money.ts, quantity.ts, valuation.ts, vat.ts, invoicing.ts  точни суми, количества, себестойност, ДДС, фактури
    plans.ts      абонаменти и лимити
    integrations/ core.ts (данни за достъп, HTTP, дневник), couriers/ (Еконт, Спиди, BOX NOW), shops/ (WooCommerce, Shopify)
    accounting.ts, accounting-export.ts  данни и файлове за счетоводителя
    reports.ts    изчисления за Отчети
    auth.ts, permissions.ts, audit.ts, webhooks.ts, api.ts, csv.ts, settings.ts, forms.ts, utils.ts
  app/api/        export/[kind] (CSV), v1/* (REST API), v1/openapi.json
  app/docs/       API документация: Swagger UI + четима версия (публични)
  app/(mobile)/m  мобилен режим (PWA), app/(help)/help — помощ, app/(legal) — правни страници
  lib/openapi.ts  OpenAPI 3.1 спецификация — единствен източник за документацията
```

Правила: страниците са server components, които четат чрез `lib/queries.ts` и
променят чрез `lib/actions/*`. Само формите, които изискват интерактивност, са
client components.
